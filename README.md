# 시스템프로그래밍 7주차 과제 — 파이프와 FIFO

파이프로 부모-자식이 통신하고, dup2 로 명령을 이어 붙이고, FIFO 로 남남끼리 통신한다.

| 파일 | 원본 | 내용 |
|---|---|---|
| `1_pipe.c` | `original/1_pipe_basic.c` | `./1_pipe "hello world"` — 부모가 보낸 문자열을 자식이 대문자로 바꿔 돌려줌 |
| `2_pipeline.c` | `original/2_pipe_dup2.c` | `./2_pipeline ls -l : wc -l` — `:` 로 나눈 두 명령을 파이프로 연결 |
| `3_fifo_read.c` / `4_fifo_write.c` | `original/3_fifo_read.c` / `original/4_fifo_write.c` | FIFO 로 메시지 주고받기 / 받는 쪽이 quit 까지 반복 수신하도록 변경 |

## 빌드 / 실행 (WSL2)

```bash
make
./1_pipe "hello world"
./2_pipeline ls -l : wc -l
./3_fifo_read          # 터미널 A (먼저 실행)
./4_fifo_write 안녕    # 터미널 B
./4_fifo_write quit    # 터미널 B — 받는 쪽 종료
```

## 1. 1_pipe — 파이프 두 개로 문자열 왕복

1번 과제 변경점
``` 1번 과제 / 변경점
1. #include <ctype.h> 추가
- 대문자로 바꾸는 toupper 를 쓰기 위해 추가

2. int fd[2] 하나였던 파이프를 int p2c[2], c2p[2] 두 개로 변경
- 파이프는 한 방향으로만 흐르기 때문에 왕복하려면 두 개가 필요함
- p2c = 부모→자식, c2p = 자식→부모

3. main(void) 를 main(int argc, char *argv[]) 로 변경
- ./1_pipe "hello world" 처럼 인자로 받은 문자열을 보내도록 변경
- 인자가 없으면 사용법을 출력하고 종료

4. 자식: close(fd[1]) 을 close(p2c[1]); close(c2p[0]); 로 변경
- 자식은 p2c 에서 읽고 c2p 에 쓰기 때문에 안 쓰는 두 끝을 닫음

5. 자식: read 한 뒤에 toupper 로 대문자로 바꾸고 write(c2p[1], buf, n) 추가
- 받은 문자열을 대문자로 바꿔서 부모에게 돌려보냄
- 다 쓰고 close(c2p[1]) 해야 부모의 read 가 끝남

6. 부모: close(fd[0]) 을 close(p2c[0]); close(c2p[1]); 로 변경
- 부모는 p2c 에 쓰고 c2p 에서 읽기 때문에 안 쓰는 두 끝을 닫음

7. 부모: write → close(p2c[1]) 한 다음에 read(c2p[0], ...) 추가
- 보내고 닫은 뒤에 자식이 돌려준 대문자 문자열을 읽어서 출력
- 쓰기 전에 읽으려고 하면 자식도 읽기를 기다리고 있어서 둘 다 멈추기 때문에 순서가 중요함
```

## 2. 2_pipeline — dup2 로 명령 이어 붙이기

2번 과제 변경점
``` 2번 과제 / 변경점
1. #include <string.h> 추가
- ":" 를 찾는 strcmp 를 쓰기 위해 추가

2. main(void) 를 main(int argc, char *argv[]) 로 변경
- ./2_pipeline ls -l : wc -l 처럼 명령을 인자로 받도록 변경

3. argv 에서 ":" 를 찾아 그 자리를 NULL 로 바꾸고 cmd1, cmd2 포인터로 나눔
- argv: [./2_pipeline] [ls] [-l] [:] [wc] [-l] [NULL]
- ":" 자리를 NULL 로 바꾸면 배열이 두 토막으로 갈라짐
- cmd1 = &argv[1] → "ls" "-l" NULL
- cmd2 = &argv[4] → "wc" "-l" NULL
- ":" 가 없거나 앞뒤 명령이 비어 있으면 사용법 출력 후 종료

4. execlp("ls", "ls", NULL) 을 execvp(cmd1[0], cmd1) 로 변경
   execlp("wc", "wc", "-l", NULL) 을 execvp(cmd2[0], cmd2) 로 변경
- execlp 는 인자를 하나씩 나열하는 방식이고 execvp 는 배열로 넘기는 방식
- 실행 전에는 어떤 명령인지 모르기 때문에 배열로 넘기는 execvp 를 사용

5. 파이프, dup2, close, wait 구조는 원본 그대로
- 첫 번째 자식: 표준출력(1)을 파이프 쓰기 끝으로 dup2
- 두 번째 자식: 표준입력(0)을 파이프 읽기 끝으로 dup2
- 부모는 양쪽 다 닫아야 두 번째 명령이 EOF 를 보고 끝남

~ 확인 결과
- ./2_pipeline ls -l : wc -l 과 셸에서 ls -l | wc -l 을 실행한 결과가 15 로 같음
```

## 3. 3_fifo_read / 4_fifo_write — FIFO 로 메시지 주고받기

3번 과제 변경점
``` 3번 과제 / 변경점
*** 원본이 이미 받는 쪽·보내는 쪽 한 쌍이라 한 번만 주고받고 끝나는 것을
    여러 번 주고받을 수 있도록 받는 쪽만 변경해 보았습니다 ***

[3_fifo_read.c]
1. #include <string.h> 추가
- "quit" 비교를 위한 strcmp 를 쓰기 위해 추가

2. open → read → close 한 번만 하던 것을 while (1) 루프로 감쌈
- 보내는 쪽이 close 하면 read 가 0(EOF) 을 돌려주고 그 뒤로는 계속 0 이라
  다음 메시지를 받으려면 FIFO 를 다시 open 해야 함
- 그래서 루프 안에서 매번 open → read → close 를 반복

3. 받은 메시지가 "quit" 이면 break
- 루프를 빠져나온 뒤 unlink(FIFO_PATH) 로 FIFO 파일을 지움

[4_fifo_write.c]
- 변경 없음 (인자 하나를 받아서 보내고 닫는 구조가 이미 보내는 쪽으로 완성되어 있음)

~ 확인 결과
- 터미널 A 에서 ./3_fifo_read 실행 → open 에서 멈춰서 기다림
- 터미널 B 에서 ./4_fifo_write 안녕, 두번째, quit 세 번 실행
- 터미널 A 에 세 메시지가 순서대로 찍히고 quit 에서 종료됨
- ls -l /tmp/sysprog_fifo → No such file or directory (unlink 로 지워진 것 확인)
```

### 이번 과제를 하면서 이해한 내용

1. **파이프는 한 방향으로만 흐른다**
   pipe() 로 만든 파이프는 fd[1] 로 넣고 fd[0] 으로 꺼내는 한 방향 통로라서
   왕복하려면 파이프가 두 개 필요하다는것을 알게 되었습니다.

2. **안 쓰는 fd 를 닫아야 EOF 가 온다**
   read() 가 0 을 돌려주는 조건은 그 파이프의 쓰기 끝이 하나도 안 남았을 때입니다.
   fork 하면 쓰기 끝이 부모와 자식 둘 다에 생기기 때문에 읽는 쪽이 자기 쓰기 끝을 안 닫으면
   자기가 자기를 막아서 영원히 기다리게 된다는것을 알게 되었습니다.

3. **(과제 1) 부모가 쓰고 → 닫고 → 읽는 순서여야 하는 이유**
   부모가 쓰기 전에 먼저 읽으려고 하면 자식도 부모가 보내길 기다리고 있어서
   둘 다 영원히 기다리는 교착 상태가 된다는것을 알게 되었습니다.

4. **(과제 2) dup2 가 하는 일**
   dup2(a, b) 는 b 번호로 접근하면 a 가 가리키던 곳으로 가게 만듭니다.
   자식에서 표준출력(1)을 파이프 쓰기 끝으로 바꿔치기하고 exec 하면
   ls 는 평소처럼 화면에 쓰는 줄 알지만 실제로는 파이프로 흘러간다는것을 알게 되었습니다.
   셸의 | 가 이렇게 동작한다는것을 알게 되었습니다.

5. **(과제 2) 부모가 파이프 양쪽을 안 닫으면 wc 가 안 끝나는 이유**
   부모가 쓰기 끝을 열어 두면 wc 입장에서는 아직 쓸 사람이 남아 있는 것이라
   EOF 를 못 받고 계속 기다린다는것을 알게 되었습니다.

6. **(과제 3) FIFO 의 open 이 멈추는 이유**
   FIFO 는 이름이 있는 파이프라서 관계없는 두 프로그램도 같은 경로로 연결할 수 있습니다.
   open(O_RDONLY) 은 반대쪽이 열릴 때까지 기다리기 때문에
   받는 쪽을 먼저 실행하면 멈춘 것처럼 보이는데 그게 정상이라는것을 알게 되었습니다.

7. **(과제 3) 매번 다시 open 하는 이유**
   보내는 쪽이 close 하면 받는 쪽 read 가 0(EOF) 을 돌려주고 그 뒤로는 계속 0 이라
   다음 메시지를 받으려면 FIFO 를 다시 open 해야 한다는것을 알게 되었습니다.
